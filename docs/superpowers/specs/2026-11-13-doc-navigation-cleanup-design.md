# 文档导航清理：设计

日期：2026-11-13；主题：`doc-navigation-cleanup`；修订：R4；模式：`mode=default`。

## 背景

文档审查确认当前可见的 534 份 Markdown 中，`docs/superpowers` 占 513 份、44,844 行。根入口主要提供使用说明，缺少稳定的分类导航；部分入口仍链接已按用户要求合并并删除的旧工作包。`AGENTS.md` 末尾还残留一段外来建议修改模板，不属于项目规则。

## 目标

- 恢复 `AGENTS.md` 的单一职责，只保留项目协作和交付规则。
- 将已删除旧账本的引用改指当前有效后继账本。
- 建立集中、简短、可扩展的文档总入口，使读者能够按目标进入生产说明、架构资料、产品设计和工作包历史。
- 保持历史文件和历史证据原位。

## 方案

新增 `docs/README.md` 作为统一索引。根 README 的“生产文档”调整为“文档导航”，首先链接总入口，再保留高频生产说明。总入口按四类组织：使用与生产、架构与开发、产品与设计、工作包与历史。

旧 2026-10-29 本地项目工作区和 2026-11-02 智能体操作授权账本已按既有文档记录合并到 2026-11-03 页面工作包，因此：

- 项目会话、权限和授权证据改指 `2026-11-03-projects-page-ledger.md`。
- 本机客户端配对、撤销和远程链路证据改指 `2026-11-03-local-client-page-ledger.md`。
- 2026-07-28 计划第 456 行位于 fenced code sample，展示的是仓库根 README 应写入的链接；原 `docs/tool-development-guide.md` 在该目标文档中正确，因此不改写历史示例。

## 约束

- 不改写历史发布说明正文，只替换其中失效的后继链接。
- 不移动、重命名或删除 `docs/superpowers` 下的历史文件。
- R0 不纳入 P2 的技术架构刷新和来源矩阵；R1 已按用户追加确认完成这两项，但仍不整理 2026-11-09/2026-11-12 工作包。
- 工作树存在大量既有未提交修改，所有改动必须限定在已确认文档范围。

## 验收

- `AGENTS.md` 在第 228 行正常结束，无 230 行后的外来模板和未闭合围栏。
- 排除 fenced code sample 后扫描本地 Markdown 链接，原 3 个真实错误目标消失，且没有本次新增失效链接。
- 根 README 链接到 `docs/README.md`，总入口中的全部本地路径存在。
- 本次六份工作包互相链接且状态一致。

## 修订 R1：P2 当前事实刷新

### 背景与证据

初始盘点发现能力说明存在版本漂移：根 README 已描述控制台编辑、删除、显式停止、流式会话和 11 个 v2 入口，而技术架构、部署指南和路线图仍保留“手动取消未交付”等旧口径。迁移脚本实际已到 V31，旧文档只列到 V9 附近的版本，难以帮助部署人员判断当前结构范围。

相关证据包括当前 `cm-agent-console` 的 11 个 HTML 入口、`ConversationController` 的 cancel/SSE 路由、`LocalClientController` 与 `LocalProjectController`、`CmAgentFlyway` 的方言加载逻辑，以及 V1–V31 迁移文件。

### 设计

在 `docs/README.md` 增加“当前事实来源矩阵”，明确代码/配置/测试、专项生产文档、README、发布说明和工作包历史的优先级。

三份专项文档采用不同深度：

- `technical-architecture.md` 解释稳定架构、运行链路、迁移分组和三类能力边界。
- `deployment.md` 保留部署步骤，并按迁移职责分组；具体版本继续以迁移目录和 Flyway 历史为准。
- `roadmap.md` 记录阶段 3 后的已交付增量，同时保留阶段 4/5 未交付状态。

### 验收

- 事实矩阵能明确冲突时选择哪份文档。
- 三份文档均不再把显式停止写成未交付能力。
- 迁移头、控制台入口数、默认关闭能力和未交付范围与当前代码/配置一致。
- 不修改 2026-11-09、2026-11-12 工作包和业务代码。

## 修订 R2：P3 工作包状态目录

### 背景

`docs/superpowers` 原先只有 30/512 个工作包文件被 README 直接索引，读者需要按日期猜测当前主题和最新证据。用户要求提供 112 个工作包的统一状态目录；盘点在 P0–P2 之前得到 112 组，本次文档整理本身形成第 113 组，因此目录按当前事实收录 113 组并说明基线差异。

### 方案

新增 `docs/superpowers/WORKPACK-STATUS.md`，按月份和日期倒序展示：

- 日期与主题。
- 已有文档类别数量。
- 文档中显式声明的最高修订号；未声明时显示“未声明”，不推测。
- 最新进度账本；缺少账本时显示“—”。
- 当前 Git 快照中的未提交状态。
- 后续入口：优先提示词，其次计划或账本，并明确提示词只是形成时输入。

`docs/superpowers/README.md` 保留长期需求组摘要，并增加完整状态目录入口。`docs/README.md` 在事实来源矩阵和历史导航中加入该目录。

### 验收

- 当前 113 组全部出现一次。
- 2026-11-09 delivery、2026-11-12 Sites 和 2026-11-13 本次工作包的 Git 状态准确显示。
- 13 个缺少进度账本的主题明确标为 `—`，不用旧文档补造。
- 状态目录自身链接全部存在，不移动或删除任何工作包。

## 修订 R3：P4 六件套职责收紧

### 问题与决定

现有历史和技能契约允许清单、计划、提示词、实现说明与账本同时维护状态及证据，导致修订时需要在多份文件复制状态、命令结果和提交信息。R3 决定：

- 进度账本是实时状态、实际证据、命令结果、阻塞、提交和发布信息的唯一入口。
- 清单只定义稳定任务、依赖和验收；提示词只保存执行输入；设计只记录方案与决定；计划只记录方法和顺序；实现说明只记录实际改动和设计差异。
- 其他五份可以摘要并链接账本，但不复制状态表。
- 已存在的历史工作包保留原文；新工作包和后续修订执行新规则，旧包再次修订时只迁移本次触及的内容。

本轮选择 `2026-10-01-remote-docker-password-auth` 作为首个历史迁移组。选择依据是它是完整六件套、已纳入版本控制、没有并行修改，且迁移前最大两两相似度 0.715、平均相似度 0.499，为当前最高。迁移采用自然下一修订 R2：R0 原文继续归档，非账本文件收敛为固定职责，R1 的完整执行状态和验证证据保留在账本。

### 实施边界

同步修改项目 `AGENTS.md`、本地 `requirement-workpack` 技能主流程、产物契约和界面描述。当前维护工作包从 R3 起按新规则追加职责，不批量清理 R0–R2 的状态历史。

### 验收

- 规则文件与技能契约均明确“账本唯一状态源”。
- 当前 R3 任务只在账本记录状态和验证结果。
- `WORKPACK-STATUS.md` 显示本工作包 R3 和 `remote-docker-password-auth` R2。
- `remote-docker-password-auth` 迁移后的最大相似度低于迁移前 0.715，平均相似度低于 0.499。
- 不修改业务代码、配置、已有工作包内容或 2026-11-09/2026-11-12 工作包。

## 修订 R4（2026-11-13）：下一批高重复历史组迁移

本修订目标是降低历史工作包跨文件复制，同时保持历史证据可追溯。选择规则以六份活动区的跨文件文本重复度为主，并以已有自然修订为迁移边界。

### 设计决定

| 编号 | 决定 | 理由 |
|---|---|---|
| D4-1 | 先补齐 skill-import-description 的账本，再开始新组 | 让上一批六件套真正达到单一状态源 |
| D4-2 | workspace-directory-selection-implementation 从 R2 升到 R3 | 它是未迁移组中重复度最高者，且 R2 是现有自然修订点 |
| D4-3 | skill-sandbox 从 R1 升到 R2 | 它是下一高重复组，并拥有完整历史六件套和可独立保留的 R1 账本 |
| D4-4 | 只迁移文档职责，不重新验证历史业务 | 用户本轮要求整理文档；历史实现和测试不能因改写而获得新结论 |
| D4-5 | 迁移前全文原样折叠归档 | 保留修订来源、旧证据适用性和后续审计能力 |

### 非目标

- 不合并或删除历史工作包。
- 不改变业务源码、配置、数据库、迁移或运行中的服务。
- 不修改 2026-11-09 和 2026-11-12 工作包。

R4 状态与证据只记录在[进度账本](../progress/2026-11-13-doc-navigation-cleanup-ledger.md)。
