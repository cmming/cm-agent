# 本机客户端项目工作区实施设计

## R5 当前设计差异：T9/T17 平台恢复续验（2026-11-11）

- **新增（可操作性）：** `ClientProjectFenceJournal` 将见证文件或指定 Run 记录缺失定义为类型化 `MissingWitnessException`；轮询捕获后转换固定安全说明并退出，指引运维显式执行 `init-fence-store`，不再把不可自愈的迁移状态显示成普通网络握手故障。
- **澄清（证据边界）：** 强制终止客户端后 Job Object 随句柄关闭结束整棵受管进程树，等价覆盖崩溃、注销和断电后的强制进程回收路径；仍不能证明物理断电时长、系统重启恢复或交互式会话注销的全部平台行为，T9/T17 保持进行中。
- **调整（恢复判定）：** 双实例只允许由数据库行锁和条件更新产生一个代次赢家；获胜实例后续心跳与设备确认共同决定 Run 收口。失败竞争实例继续观察到新归属后必须停止续租，不能以本地缓存句柄或旧代次继续授权。
- **不变：** 无见证 Run 不自动补造首代，恢复阶段不重放命令/文件变更，设备签名、根身份、项目来源和租户/主体过滤均不放宽。

## R4 历史收口：T19 可信代次与安全恢复（2026-11-11）

- 协议采用服务端权威的单一归属行与单调代次。首代为 `EXECUTING`；租约过期后只能原子推进到 `RECOVERING`，设备必须先持久记录该代次，再通过签名请求确认，Server 才可把 Run 安全收口为 `FAILED`。
- 任务按运行级和项目级区分。运行级任务必须同时带 Run、根、正代次与阶段；服务端对项目级任务显式返回 `epoch=0`，客户端将其视为无代次，避免 Jackson 的非空 `Long` 判断误伤目录选择等任务。
- 设备确认与任务领取顺序为设备、归属、确认、任务的行锁顺序。恢复阶段只允许 `COMMAND_STATUS` 与 `STOP_COMMAND`；已发出的启动、文件变更和命令不得因恢复再次获得执行权。
- Run 终态的最终写入和归属关闭属于同一短事务。终态 Run 不再参与续租、过期接管或未确认代次查询，从而阻止恢复行到期后产生无意义的新代次。
- 匿名挑战限流按“服务端观测来源 + 请求设备标识”分桶。该键不替代设备存在性和签名验证，只防止同一来源多设备正常轮询共用单一预算。
- 验收以提交 `9fff872` 为准：真实 Windows 上观察到 `RUNNING` Run、精确 HIGH 审批、命令启动、Server 停机 36 秒、客户端存活、恢复代次 2、命令 `UNKNOWN`、Run `FAILED` 和零重放；Rocky PostgreSQL 16/MySQL 8.4 定向测试全部通过。

以下 T19 小节保留形成 R4 前的设计演进；其中“尚未接入、未完成”均不覆盖本节。

## 实施原则

- R3 续验约束：项目任务标识与业务操作标识分离，目录登记及结果回报使用 taskId；搜索词必填只对 SEARCH 生效，所有查询仍校验长度和 NUL。T6/T17 的验收使用已提交且远端对齐的源代码，保留用户配置和无关修改。
- 新功能使用独立配置和来源，默认关闭；既有 Server 本机项目、普通聊天和通用本机客户端保持原行为。
- 新来源的关键数据链为：已认证浏览器创建选择请求 → 配对设备签名领取 → 用户在本机确认目录 → 客户端返回 rootId/身份摘要/展示名 → Server 建立项目及长期来源 → 后续请求按设备任务执行。
- Server 不保存客户端绝对路径；客户端状态和根绑定使用当前 OS 用户私有目录及跨进程锁。文件 I/O 不持有 JDBC 事务。
- UI 查询采用有界异步任务；模型工具可在受控时间内等待，但命令启动后的生命周期由持久操作和独立状态入口承载。
