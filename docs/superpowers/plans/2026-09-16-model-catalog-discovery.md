# 模型配置远程模型目录发现实施计划

## 前置结论

本计划对应“模型名称可从接口获取”的前后端改动。页面采用显式获取、下拉选择与手工输入兜底；发现请求由服务端代发，不能把 API Key 交给浏览器。具体安全约束见[设计](../specs/2026-09-16-model-catalog-discovery-design.md)。

## 任务拆分

1. **领域与出站契约（已完成）**：在 server 中定义受控失败类型、独立配置与可替换传输契约；不向 `ModelConfig` 增加持久化字段。
2. **安全出站客户端（已完成）**：复用 URL 安全校验并使用独立主机白名单，禁止重定向，限制超时、响应体与模型数；第一版不自动分页。
3. **目录解析（已完成）**：统一解析两类供应商基础地址返回的 `data[].id`；`404`、`405` 映射为稳定“不支持”，无效 JSON/结构映射为受控格式错误。
4. **应用服务与凭据边界（已完成）**：草稿请求只用临时 API Key；已保存配置只从当前 tenant 与 ID 读取原始地址和密文，生成审计、诊断日志及 `errorId`。
5. **Web API（已完成）**：新增草稿及已保存配置两种发现入口，接入 `model:write`、可信主体、校验和统一异常响应。
6. **控制台交互（已完成）**：新增“获取模型列表”按钮、加载/刷新/错误状态、datalist 候选和手工输入回退；编辑时按地址/Provider 变更控制旧凭据复用。
7. **测试与文档（已完成）**：服务层 4 项、Controller 7 项、Node 控制台 69 项与控制台 Maven 测试通过；本地 test profile 已启动并验证健康检查与页面资源。全量 Maven 测试因本机 Docker 不可用而无法运行既有 Testcontainers 套件，详情记录在进度账本。

## 预期文件范围

- `cm-agent-server`：模型发现服务、出站客户端/配置、`ModelConfigController`、统一异常和 Web 测试。
- `cm-agent-console`：`model-configs.html`、`assets/app.js`、控制台资源与脚本测试。
- `cm-agent-core`：仅在确有跨模块复用必要时增加无框架依赖的发现契约。
- `README.md`、`docs/configuration.md`、`docs/operations.md`、`docs/release-notes.md`：实现后更新用户可见边界、白名单和运行限制。

## 实施顺序

先完成出站安全策略与 Provider 解析单元测试，再接入已保存凭据和草稿凭据两条服务路径；随后暴露 Controller，最后连接控制台。控制台不得在后端安全测试未完成前直连供应商。实现后再更新生产文档并完成浏览器烟测。

## 验证方式

- 使用 Java 21 执行模型发现服务和 Web 定向测试。
- 执行 `mvn -q -pl cm-agent-console -am test` 与 Node 控制台脚本测试。
- 在具备与本地提交一致工作区的 Rocky Linux Docker/Testcontainers 环境中执行涉及 JDBC 的验证；本需求原则上不修改 schema。
- 使用真实浏览器完成创建、编辑、刷新、手工输入、权限拒绝、超时和不支持 Provider 的烟测，确认浏览器未向供应商域名发起请求。

## 风险与决策

第一版不增加目录缓存、能力标签或价格字段；这是为了优先保证密钥和地址边界正确。若后续需要缓存，必须以 tenant、配置 ID、Provider、规范化地址和短 TTL 为键，且先处理多实例一致性与失效语义。
